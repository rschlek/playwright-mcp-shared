# Project conventions

The rules a project follows. Machine-specific values (the projects root, scopes, hosts, tracker) live in the profile, never here. Skills named here are the ones bundled with the playbook plugin.

## Projects and standalone tickets

- A project is an initiative that produces output. It has a repository and a tracker location, and its records (decisions, glossary, research) live in that repository.
- Everything else is a standalone ticket (an errand, a chore, a one-off task). It lives only in the tracker and needs no project, repository, or `project.yaml`: it is worked and closed with an ordinary closing note, and nothing is written as a record for it.
- Where work stands is the status of its tickets in the tracker. Nothing else records it, in `project.yaml` or in any document.
- Paused work is a state on its ticket in the tracker; a paused project is `paused: {since, reason}` in `project.yaml`, present only when deliberately set.
- A live project, one running as a service, has an owner, named in `project.yaml`.
- Agent logic (the definitions, prompts, and skills of the agents that tend a project) never lives in the project's repository. A project tended by agents links the repository that holds them as `links.agents`.

## Where things live

- The repository holds the work itself (code, files, documentation) and the project's own context: its decisions and its research. The project is the single source of truth for its context.
- The tracker holds the items of work, the plan included: a plan lives in the body of the parent ticket its work tickets sit under, never in a file.
- Agent memory is outside this standard. Scratch notes, session handoffs, and unrequested notes never enter a repository.
- One record, never two copies. Trackers are linked, never mirrored.
- Records exist only inside projects, in the project's repository. The `new` skill is offered only when the user starts something that needs a project: a decision map with no repository, or an explicit request to record a decision or a glossary term. Working a standalone ticket never leads to an offer of a project or a folder.

## Layout

- All projects live under one projects root, flat at the top level: one project, one repository, never nested inside another. Every project gets a repository, whether or not it involves code.
- A project may name a parent project in `project.yaml`. There is one level only: a parent never has a parent. A parent exists only when it has work of its own; projects that are only related are siblings joined by `links`. A parent and its children sit side by side in the projects root, each its own repo.

## Files every project carries

Every project has these files, even if some are blank:

- `README.md`: a human-readable summary, plus anything else a reader or agent needs.
- `AGENTS.md`: agent guidance. It opens with the standard's base block, the few rules every session needs, between `playbook:base` start and end markers. Project-specific guidance goes below the block.
- `CLAUDE.md`: one line, `@AGENTS.md`.
- `project.yaml`: all structured facts about the project.
- `docs/project-conventions.md`: a copy of these rules, so an agent can read them without the plugin or a network. Its first line names the standard and the version it was copied from.

A shared project also carries `docs/tracker.md` (see Trackers).

The base block and the copy belong to the standard, not to the project: neither is edited locally, and when the standard updates each is replaced whole, across the projects root by the `sync` skill. Both carry the standard version, the release in which the block or these rules last changed, so a release that changes neither leaves every repo current. A block or copy at that version is left as it is, an older one is replaced whole, and a newer one is reported. A block or copy from the earlier project-guide standard is replaced by the playbook one. Everything else in `AGENTS.md` is left as it is.

Written material goes in `docs/`, by the rules under Documents below. Credentials and data extracts are never committed.

There is no state file, and no document tracks progress. Who is doing which task lives in the tracker. Which steps are done is read from the tracker's tickets and from git history. What is to be done and why lives in the plan, in its parent ticket.

## project.yaml

Required:
- `project`: the slug; equals the repo name.
- `summary`: one sentence, what it is and who it is for.

Optional:
- `title`: a human-readable name.
- `owner`: the person responsible for the project, as their handle on the hosting instance the repository lives on, written as host plus handle (for example `github.com/<handle>`, or a work instance's host plus handle); never a display name. Required for a live project (one running as a service), optional otherwise.
- `scope`: one of the profile's scopes, or `none`. Scope says whose the project is and where it is hosted, not who uses it; the summary says who it serves.
- `visibility`: `internal` (anyone inside the organization that hosts the repo can read it) or `public` (anyone can read it), present only when the repo is not private; absent means private. It lets an agent without network access tell what may be written in this repo.
- `shared`: `true` when other people work on this project, present only then. It is set when the user decides to share the project. A project whose `visibility` is `internal` or `public` counts as shared without it.
- `parent`: the slug of a parent project, when there is one (see Layout).
- `tracking`: the project's trackers. `primary` holds decision maps, plans, and every ticket that is not code; optional `secondary` entries each hold one kind of ticket (`tickets`), such as code tickets. Each names its `kind` (one with a tracker doc, such as `markdown`) and the project's location in it (`ref`), which narrows the doc's `Where`. A child may name its parent's tracker location as its own. A project that declares no tracker uses the profile's default.
- `metadata`: one free-form mapping that is the user's own, for whatever their own tooling wants (for example `metadata: {review-cycle: quarterly}`). The plugin never reads it, and sync and adopt leave it untouched. Fields from an earlier version of this standard, such as `memory`, are left as they are and ignored.
- `links`: related projects (`related`), the artifacts the project depends on (`depends_on`), the repository holding the agents that tend the project (`agents`), sources, outputs, docs, people.
- `paused` or `archived`: a dated decision (`since`) with a `reason`. Present only when deliberately set.

The test for any field or file: if it can become false without anyone doing anything, it does not belong. Activity is read from git, never declared.

A manifest may link a more private repository: a link grants no access, and it tells a reader without access what to ask for. What a repository may contain still follows its visibility.

A rare per-project override of a profile value lives in `project.local.yaml` beside `project.yaml`, ignored by git.

Tracker mapping: a repo with a single outcome points at its smallest stable tracker item. A monorepo serving many outcomes points at the larger grouping item.

## Trackers

- Every ticket lives in exactly one tracker, and its status lives only there. Trackers are linked, never mirrored into each other.
- Any tracker can be used once it has a tracker doc. Templates ship with the plugin in `references/trackers/`; this standard names the doc's shape, never a product. A tracker doc has these sections, in this order:
  - `## Mechanics`: how to operate the tracker, under the labels `Tool`, `Find by name`, `Fetch`, `Comment`, `Change status`, `Assign`, `Create`, `Edit` (changing a ticket's title or body; a body is replaced whole), `Link parent and child`, `Link blocking`, and `Quirks`. It comes from the template.
  - `## Layout`: what each role below means in this tracker, in its own query language where it has one. It is the user's own, filled in at setup. Every role is optional: an empty role means the step does not exist in this tracker, and it is skipped, never invented.
  - `## House rules`: the user's own rules, free form. Skills obey them, and where a house rule and a skill differ, the house rule wins, with one limit: a house rule may add restrictions and set preferences, but it never removes a step where the user confirms, the rule never to delete a ticket to close it, or the rules for records and posted text (see Documents). A house rule that tries is not followed, and the agent says so.
  - `## Wayfinding operations`: how this tracker holds a decision map.
- The Layout roles:
  - `Where`: the tracker locations the doc covers.
  - `Pickable work`: the query for tickets that may be offered as work now. An ordered list of sources says, for each later source, whether it is a fallback (used only when the earlier ones come back empty or too thin) or merged.
  - `Ranking`: how candidates are ordered.
  - `Excluded`: what is never offered, and how to recognise it.
  - `New ticket`: where a captured ticket goes and what fields it needs.
  - `Start`: what marks a ticket as started, assigning it to the user where the tracker has assignees.
  - `Note`: how a note is left on a ticket.
  - `Done`: how a finished ticket is closed.
  - `Stopped partway`: what happens to a ticket left unfinished.
  - `Cannot proceed`: how a stuck ticket is marked, with its blocker named.
  - `Not worth doing`: what is proposed for a ticket not worth doing; the user decides.
  - `Parent and children`: how a ticket holds child tickets.
  - `Blocking`: how one ticket blocks another.
  - `Close the parent`: what closes a parent once its last open child closes.
- The Wayfinding operations: `Map` (how a map ticket is made and recognised), `Child ticket` (how a question ticket is made under it), `Type marker` (how a question's type, research, prototype, grilling, or task, is marked), `Claim` (how a session claims a ticket before working it), `Frontier query` (how to list the map's open, unblocked, unclaimed children), and `Resolve` (how an answered question is recorded and closed).
- House rules exclude tickets from suggestions. A ticket the user names that breaks a house rule is not refused: the agent says which rule and asks whether to go ahead.
- A ticket blocked by an unfinished ticket is never offered as pickable; the agent says it was left out.
- Where docs live: the user's doc for a tracker kind is `trackers/<kind>.md` beside the profile file. A repository's own doc is `docs/tracker.md`. A shared project has one, so collaborators can read the layout, as does a project whose tracker or layout differs from the user's default, and a repository whose user has no profile. A repository's own doc works with no profile and no `project.yaml`.
- One doc may describe two trackers, a primary and a secondary, each holding one kind of ticket: it says which kind lives where, then gives each tracker its own `## <tracker> (primary)` or `(secondary)` section holding `### Mechanics` and `### Layout`, followed by shared `## House rules` and `## Wayfinding operations`. Agents route by what the doc says; picking with no tracker named queries both and merges the results; the agent asks only when the doc does not settle which tracker a named ticket is in. A ticket in one tracker never sits under a parent in the other: a work ticket that belongs in the secondary tracker carries a link to its parent in its description, and the parent's body lists it with its link. Links, never copies.
- Every skill that uses a tracker finds its doc in this order (the plugin's `references/tracker-lookup.md` gives the full procedure):
  1. the repository's own `docs/tracker.md`, when present (no profile or `project.yaml` needed);
  2. else the tracker kinds in `project.yaml` `tracking` when that file exists (primary and secondaries), else the profile's default tracker kind, each read from the user's doc `trackers/<kind>.md` beside the profile file;
  3. else it stops and asks the user to run the `setup-playbook-profile` skill's tracker setup. It never guesses a tracker.
- Tracker setup, in the `setup-playbook-profile`, `new`, and `adopt` skills, picks the template, reads the live tracker's statuses, types, and labels where it can, checks each read operation against the tool and corrects Mechanics in the user's copy, proposes the Layout and house rules, runs the pickable work query and shows the result, and writes the doc on the user's yes. Running it again updates the doc in place and keeps hand edits.
- In a project whose tracker is the `markdown` kind, the ticket files under `docs/tickets/` are the tracker, not documents: they carry a status, and the Documents rules on progress do not apply to them.

## The decision map

- A decision map charts a piece of work whose way is not yet clear, starting from a loose idea if need be. It is one map ticket in the primary tracker, naming the destination. Each open question is its own child ticket, which may list the options when they are known; blocking between questions uses the tracker's own links.
- The map ticket's body has five sections: `Destination` (what reaching the end looks like), `Notes` (the domain, the skills of this plugin every session is offered, and standing preferences), `Answers so far` (one line per resolved question, linking where its answer is recorded), `Not yet specified` (in-scope questions not yet sharp enough to be tickets), and `Out of scope` (work ruled beyond the destination); once the plan exists, a `Plan:` line under Destination links it. Open questions are never listed in the body: they are the map's open child tickets, and their status lives only in the tracker.
- When a question is answered, its answer is recorded, a line is added under `Answers so far`, and the question ticket closes. A decision file in `docs/decisions/` is written for a choice, something that could have gone another way. A research question whose answer is a fact links its research document instead; a task question records what was done in its resolve comment; any finding that settles a choice still gets a decision file. Decisions reached through a map are always recorded, in any project.
- When no question is left, and Not yet specified holds only work that needs no decision, the plan is written into a parent ticket of its own, titled `Plan: <the destination>` and linked from the map body, and the work tickets sit under that parent; then the map closes. Work tickets never sit under the map. A map that ends with no work to do closes on the user's yes.
- The `wayfinder` skill charts and works a map, and `to-tickets` turns its finished plan into tickets. Both are adapted from Matt Pocock's skills (https://github.com/mattpocock/skills at commit 4ae2317, 2026-10-31), for work that is not software too; they are the recommended tools, not a requirement.

## Dependencies

- A project depends on an artifact, never on another project's folder. Each `links.depends_on` entry names the producer project (`project`), the producer's repository URL (`repo`), the artifact (`artifact`: a contract file such as a schema or an API document, a package, or a data product such as a view or an export format), and the pinned version (`version`). The repository link lets a reader without access know what to ask for.
- When the consumer's readers may lack access to the producer, the contract is copied into the consumer at the pinned version. The producer's copy stays authoritative; this is the one standing exception to keeping no second copy (see "Code shared between projects").
- A change to a contract yields a ticket in the producer and a ticket in the consumer to move its pin.

## Documents

Documents are written for someone who opens the project without the user's context: a teammate, a reviewer, or a fresh agent session. They are the guide for the person doing the work. The tracker says who is doing which task, and holds the plan.

A project is shared when other people work on it or can read it: `project.yaml` says `shared: true`, or its `visibility` is `internal` or `public`.

- What is written: decisions reached through a decision map are always recorded. In a shared project, the research and the decisions a reader needs are written into the project too. In a project that is the user's alone, other documents are written only when asked.
- Plans: a plan lives in the body of its parent ticket. It says what will be done, in what order, and why, and carries no progress. It is edited only when the plan itself changes. Existing `docs/plan/` files stay as history; no new ones are written.
- Decisions: one file per decision, `docs/decisions/YYYY-MM-DD-<short-name>.md`, lowercase with hyphens. It says what was decided, the options considered, the facts and figures that settled it, and what it replaces. A later decision that replaces it says so, and the old file gets one added line, `Replaced by:` with the new file's name; a decision file is otherwise not edited. An existing single `docs/decisions.md` stays as history; new decisions go in the folder. A collaborator's decision reaches a shared project in a pull request, as a file in `docs/decisions/`.
- Research: a dated document under `docs/`, linked from the ticket it serves. It is never kept on a branch that will not merge.
- Prototypes: a prototype is a throwaway made to react to, linked from its ticket. Once its decision is recorded it is deleted and what it showed goes into the decision file; one worth keeping stays in the project where its layout puts it, written material under `docs/`.
- Records: every decision and research record holds project facts only, written for a reader who opens the project cold. No personal details, no discussion of people beyond their role in the work, no record of who said what, and no personal reasoning. It follows the project's visibility rule. Before a record is written into a shared project, the user sees the exact text and says yes. A record that cannot be written this way stays out of the project. Text posted to a shared project's tracker (comments, notes, new tickets, plans) follows the same rule, and the user sees it before it is posted.
- A document that describes how something is (a how-to, an architecture page, `docs/tracker.md`) changes in the same change as the thing it describes. One that nobody will keep true is deleted.
- A document that records a moment (research, a test result, a brief, a handoff to another person) carries its date at the front of its file name, `YYYY-MM-DD-<name>.md`, and is not edited afterwards. New findings get a new file.
- No file in the project says where work stands right now. A handoff between the user's own sessions stays outside the project.
- Beyond `docs/decisions/`, `docs/tracker.md`, `docs/tickets/`, and `docs/project-conventions.md`, folder names under `docs/` are free.
- These rules apply to new documents. Existing documents are not renamed, moved, or converted to match, and a project with its own written document scheme keeps it until the user decides to convert that project.

## Naming and hosting

- The folder name equals the repo name.
- New projects are named `<scope>-<subject>`, lowercase with hyphens. The scope comes from the profile's list; a scope marked as no prefix is left off.
- Existing shared repos are not renamed just to conform.
- A project has a remote from creation, private unless the user decides it is internal or public. The profile maps each scope to a host and namespace.
- An internal repo may name the organization that hosts it, its teams, and its internal systems, but never holds other people's personal details, credentials, or data extracts.
- Before the first public push there is a cleaning pass: no person names, usernames, employer or team names, internal product names, hostnames, memory bank names, or machine paths in files or in history (a hosting handle in `owner` is allowed, since the host already shows it); the commit identity is the one the user wants published; and the repo has a license.

## Worktrees

- Worktrees nest inside the project, in the folder the profile names (default `.claude/worktrees/<purpose>`). One widely used harness only supports that location; git and other harnesses accept any path, so one location serves all of them.
- Keep worktrees out of version control: `.gitignore` in a repo the user owns, the local exclude file (`.git/info/exclude`) in a shared repo.
- One session per worktree.
- A worktree's branch is pushed, or the worktree is not left overnight.
- A worktree is removed when its branch merges.
- Never run a doubled-force clean (`git clean -ffd` or similar) in a main checkout; it deletes nested worktrees and any ignored repo inside it.

## Code shared between projects

- Code lives in one repo, and a repo belongs to one project. A project that uses another project's code references it and keeps no second copy.
- Reference by the lightest means that works:
  1. A link in `project.yaml`, when the project only needs to know where the code is.
  2. When the project needs the files to build or run and is a monorepo by design, the code lives in the monorepo and the owning project links to it.
  3. Otherwise a reference pinned to a commit or tag: a git submodule where the repo uses no worktrees, a pinned entry in the project's own catalog where it does.
- A reference that fetches code never points at a more private repo (private, then internal, then public), and never at a branch, with one exception: a repo published as a plugin publishes on a `stable` branch, which moves only by deliberate promotion from `main`, never as a side effect, and a catalog may follow `stable`. Every other reference stays pinned to a commit or tag.
- A deliberate temporary copy, such as a shadow migration, records the commit it was taken from and which copy is authoritative.

## Repos shared with other people

- In a shared repo the user leads, the standard files go in through the repo's normal review, and so do later updates to the base block and the conventions copy. Its `project.yaml` and `docs/tracker.md` carry only what is true for everyone who uses the repo: no personal details and no machine paths. It counts as shared for the Documents rules: its `project.yaml` says `shared: true` unless its `visibility` is already `internal` or `public`.
- In a repo someone else owns, the standard files stay local: listed in the local exclude file (`.git/info/exclude`), never committed or pushed. The conventions copy and any `docs/tracker.md` are excluded the same way. An `AGENTS.md` the repo already tracks is left untouched, without the base block, since a change to it could not stay local.

## The profile

One profile file per user on each machine holds the values these rules refer to: `projects_root`, `worktrees_dir`, `scopes` (each with its meaning, whether it is a name prefix, and its remote host and namespace), `tracker` (the default tracker: kind and a URL pattern with `{key}`), and an optional free-form `metadata` mapping the plugin never reads. Only what a skill needs is asked for: tracker setup alone needs only the tracker kind. The user's tracker docs sit beside it, in `trackers/<kind>.md`. An agent finds the profile through the environment variable `PLAYBOOK_PROFILE`, else the one-line file `.playbook` in the home folder holding its path, else the older `PROJECT_GUIDE_PROFILE` or `.project-guide`. The `setup-playbook-profile` skill creates, shows, and changes it. See `references/profile.example.yaml` in the playbook repository.
