# Project conventions

The rules a project follows. Machine-specific values (the projects root, scopes, hosts, tracker, memory system) live in the profile, never here.

## Projects and items

- A project is work with its own home: one repository, one tracker location, and one memory tag. Everything else is an item (a task, an errand, an idea), which has no home of its own.
- A project's work runs in cycles. A cycle moves through the stages idea, shaped, reviewed, planned, building, done, and paused. The stages belong to a cycle, not to the project's life: done closes a cycle, and a project with no open cycle is maintained. A cycle's stage is held in the project's primary tracker, never in a document.
- The reviewed stage produces the cycle's decision map: the list of the cycle's open decisions, each with its options. Each open decision is a ticket in the primary tracker; when it is answered, the answer and its why go in `docs/decisions.md` and the ticket closes. The standard adopts the wayfinder, to-spec, and to-tickets flow of Matt Pocock's skills (from https://github.com/mattpocock/skills at commit 4ae2317, 2026-10-31), adapted for work that is not software; those skills are the recommended tools, not a requirement.
- Paused work is a state on its item in the tracker; a paused project is `paused: {since, reason}` in `project.yaml`, present only when deliberately set.
- A live project, one running as a service, has an owner, named in `project.yaml`.
- Agent logic (the definitions, prompts, and skills of the agents that tend a project) never lives in the project's repository. A project tended by agents links the repository that holds them as `links.agents`.

## Layout

- All projects live under one projects root, flat at the top level: one project, one repository, never nested inside another. Every project gets a repository, whether or not it involves code.
- A project may name a parent project in `project.yaml`. There is one level only: a parent never has a parent. A parent exists only when it has work of its own; projects that are only related are siblings joined by `links`. A parent and its children sit side by side in the projects root, each its own repo.

## Files every project carries

Every project has these files, even if some are blank:

- `README.md`: a human-readable summary, plus anything else a reader or agent needs.
- `AGENTS.md`: agent guidance. It opens with the standard's base block, the few rules every session needs, between `project-guide:base` start and end markers. Project-specific guidance goes below the block.
- `CLAUDE.md`: one line, `@AGENTS.md`.
- `project.yaml`: all structured facts about the project.
- `docs/project-conventions.md`: a copy of these rules, so an agent can read them without the plugin or a network. Its first line names the standard and the version it was copied from.

The base block and the copy belong to the standard, not to the project: neither is edited locally, and when the standard updates each is replaced whole, across the projects root by the sync skill. Both carry the standard version, the release in which the block or these rules last changed, so a release that changes neither leaves every repo current. A block or copy at that version is left as it is, an older one is replaced whole, and a newer one is reported. Everything else in `AGENTS.md` is left as it is.

Written material goes in `docs/`, by the rules under Documents below. Credentials and data extracts are never committed.

There is no state file, and no document tracks progress. Who is doing which task lives in the tracker. Which steps are done is read from the tracker's items and from git history. What is to be done and why lives in the project's plans.

## project.yaml

Required:
- `project`: the slug; equals the repo name.
- `summary`: one sentence, what it is and who it is for.

Optional:
- `title`: a human-readable name.
- `owner`: the person responsible for the project, as their handle on the hosting instance the repository lives on, written as host plus handle (for example `github.com/<handle>`, or a work instance's host plus handle); never a display name. Required for a live project (one running as a service), optional otherwise.
- `scope`: one of the profile's scopes, or `none`. Scope says whose the project is and where it is hosted, not who uses it; the summary says who it serves.
- `visibility`: `internal` (anyone inside the organization that hosts the repo can read it) or `public` (anyone can read it), present only when the repo is not private; absent means private. It lets an agent without network access tell what may be written in this repo.
- `shared`: `true` when other people work on this project, present only then. It is set when the user decides to share the project. A project whose `visibility` is `internal` or `public` counts as shared without it.
- `parent`: the slug of a parent project, when there is one (see Layout).
- `tracking`: the project's trackers. `primary` holds the stage of each cycle, the decision map (one ticket per open decision), and every ticket that is not code; optional `secondary` entries each hold one kind of ticket (`tickets`), such as code tickets. Each names its `kind` and the project's location in it (`ref`). A child may name its parent's tracker location as its own. A project that declares no tracker uses the profile's default.
- `memory`: `tag`, `project:<slug>`; `system`, the one kind of memory the project uses: `personal`, `shared`, or `repo`; and a state model, as applicable. Never the name of a bank, an instance, or a server: the profile maps each kind to the user's actual location.
- `links`: related projects (`related`), the artifacts the project depends on (`depends_on`), the repository holding the agents that tend the project (`agents`), sources, outputs, docs, people.
- `paused` or `archived`: a dated decision (`since`) with a `reason`. Present only when deliberately set.

The test for any field or file: if it can become false without anyone doing anything, it does not belong. Activity is read from git, never declared.

One-way pointers apply to memory only: a repository never names a memory location more private than itself, and `memory` names only a kind. A manifest may link a more private repository: a link grants no access, and it tells a reader without access what to ask for. What a repository may contain still follows its visibility.

A rare per-project override of a profile value lives in `project.local.yaml` beside `project.yaml`, ignored by git.

Tracker mapping: a repo with a single outcome points at its smallest stable tracker item. A monorepo serving many outcomes points at the larger grouping item.

## Trackers

- Every ticket lives in exactly one tracker. Trackers are never mirrored into each other, and a ticket's status lives only in its tracker.
- A tracker kind is valid when a recipe exists for it: a skill that says how to create, read, update, and close a ticket there. This standard names the field shape and that contract, never a product.

## Dependencies

- A project depends on an artifact, never on another project's folder. Each `links.depends_on` entry names the producer project (`project`), the producer's repository URL (`repo`), the artifact (`artifact`: a contract file such as a schema or an API document, a package, or a data product such as a view or an export format), and the pinned version (`version`). The repository link lets a reader without access know what to ask for.
- When the consumer's readers may lack access to the producer, the contract is copied into the consumer at the pinned version. The producer's copy stays authoritative; this is the one standing exception to keeping no second copy (see "Code shared between projects").
- A change to a contract yields a ticket in the producer and a ticket in the consumer to move its pin.

## Memory

- The repository is the record a stranger needs to do the work. Memory is the working knowledge: preferences and rulings across projects, operational facts about running systems, dead ends, and where a session left off.
- The profile, written by the standard's own skills, maps each memory kind to the user's actual memory location. When no profile is present, or the project's memory is not reachable by the person working, an agent writes only what the Documents rules already allow: decisions in `docs/decisions.md`, plans in `docs/plan/`, and documents someone asked for, such as research or specs, under `docs/`. Scratch notes, session handoffs, and unrequested notes never enter a repository.
- A project uses one memory kind: `personal`, `shared`, or `repo`. A project with collaborators declares `shared`. A person's own observations go to their personal memory and are never declared in the repository.
- Context for collaborators is published into the shared location, never granted through access to a personal one. A collaborator's decision reaches the project in a pull request, as an entry in `docs/decisions.md`.

## Documents

Documents are written for someone who opens the project without the user's memory: a teammate, a reviewer, or a fresh agent session. They are the guide for the person doing the work. The tracker says who is doing which task, and the memory system holds the user's own rulings and reasoning.

A project is shared when other people work on it or can read it: `project.yaml` says `shared: true`, or its `visibility` is `internal` or `public`.

- In a shared project, the plan for a piece of work, the research behind it, and the decisions a reader needs are written into the project, not only held in memory. In a project that is the user's alone nothing is required, and an agent writes a plan or decision document only when asked. A plan that exists as a file lives in its project either way.
- Plans: one file per piece of work (one cycle), `docs/plan/<name>.md`, lowercase with hyphens. A plan says what will be done, in what order, and why. It opens with a title, then `Written:` with the date and `Task:` with the tracker item when there is one. It carries no progress: no checkboxes, no status line, no owner, no last-updated date. It is edited only when the plan itself changes.
- When the work ends (its cycle reaches done, or is dropped), the plan gets a `Closed:` line (finished or dropped, the date, one sentence on the outcome) and moves to `docs/plan/closed/` in the same change. What sits in `docs/plan/` itself is the list of open plans; no other list is kept.
- Decisions: one file, `docs/decisions.md`, newest first. Each entry has a date, what was decided, and why. A decision that changes gets a new entry that says what it replaces, and the old entry stays. Only decisions a reader needs to do or check the work go in.
- A document that describes how something is (a how-to, an architecture page) changes in the same change as the thing it describes. One that nobody will keep true is deleted.
- A document that records a moment (research, a test result, a brief, a handoff to another person) carries its date at the front of its file name, `YYYY-MM-DD-<name>.md`, and is not edited afterwards. New findings get a new file.
- No file in the project says where work stands right now. A handoff between the user's own sessions stays outside the project.
- Beyond `docs/plan/` and `docs/decisions.md`, folder names under `docs/` are free.
- Before a plan, a decision, or a record goes into a shared project it is written for the reader: what and why, not who said what in which conversation. It follows the project's visibility rule and leaves out the user's private rulings, opinions about people, and anything from a personal memory store. The first time documents are written into a project the user is about to share, the agent shows the user what it left out before committing. A document that cannot be cleaned enough stays out of the project, and the plan says where its source lives.
- These rules apply to new documents. Existing documents are not renamed, moved, or converted to match, and a project with its own written document scheme keeps it until the user decides to convert that project.

## Naming and hosting

- The folder name equals the repo name.
- New projects are named `<scope>-<subject>`, lowercase with hyphens. The scope comes from the profile's list; a scope marked as no prefix is left off.
- Existing shared repos are not renamed just to conform.
- A project has a remote from creation, private unless the user decides it is internal or public. The profile maps each scope to a host and namespace.
- An internal repo may name the organization that hosts it, its teams, and its internal systems, but never holds other people's personal details, credentials, or data extracts.
- Before the first public push there is a cleaning pass: no person names, usernames, employer or team names, internal product names, hostnames, memory bank names, or machine paths in files or in history (a hosting handle in `owner` is allowed, since the host already shows it); the commit identity is the one the user wants published; and the repo has a license.

## Worktrees

- Worktrees nest inside the project, in the folder the profile names (default `.claude/worktrees/<purpose>`). One widely used harness only supports that location; git and other harnesses accept any path, so one location serves all of them.
- Keep worktrees out of version control: `.gitignore` in a repo the user owns, the local exclude file (`.git/info/exclude`) in a shared repo.
- One session per worktree.
- A worktree's branch is pushed, or the worktree is not left overnight.
- A worktree is removed when its branch merges.
- Never run a doubled-force clean (`git clean -ffd` or similar) in a main checkout; it deletes nested worktrees and any ignored repo inside it.

## Code shared between projects

- Code lives in one repo, and a repo belongs to one project. A project that uses another project's code references it and keeps no second copy.
- Reference by the lightest means that works:
  1. A link in `project.yaml`, when the project only needs to know where the code is.
  2. When the project needs the files to build or run and is a monorepo by design, the code lives in the monorepo and the owning project links to it.
  3. Otherwise a reference pinned to a commit or tag: a git submodule where the repo uses no worktrees, a pinned entry in the project's own catalog where it does.
- A reference that fetches code never points at a more private repo (private, then internal, then public), and never at a branch, with one exception: a repo published as a plugin publishes on a `stable` branch, which moves only by deliberate promotion from `main`, never as a side effect, and a catalog may follow `stable`. Every other reference stays pinned to a commit or tag.
- A deliberate temporary copy, such as a shadow migration, records the commit it was taken from and which copy is authoritative.

## Repos shared with other people

- In a shared repo the user leads, the standard files go in through the repo's normal review, and so do later updates to the base block and the conventions copy. Its `project.yaml` carries only what is true for everyone who uses the repo: no personal memory details and no machine paths. It counts as shared for the Documents rules: its `project.yaml` says `shared: true` unless its `visibility` is already `internal` or `public`.
- In a repo someone else owns, the standard files stay local: listed in the local exclude file (`.git/info/exclude`), never committed or pushed. The conventions copy is excluded the same way. An `AGENTS.md` the repo already tracks is left untouched, without the base block, since a change to it could not stay local.

## The profile

One profile file per user on each machine holds the values these rules refer to: `projects_root`, `worktrees_dir`, `scopes` (each with its meaning, whether it is a name prefix, and its remote host and namespace), `tracker` (the default tracker: kind and a URL pattern with `{key}`), and `memory` (for each memory kind, `personal`, `shared`, and `repo`, the user's actual location; `repo` needs none). The profile skill creates, shows, and changes it. See `references/profile.example.yaml` in the project-guide repository.
